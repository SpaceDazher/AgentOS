# 60 — Математическая модель личного агентного хаба

Статус: v2, независимо проаудирован (раунд 13). Опирается на: `50_ontology.md` (классы/инварианты),
`research/sources/*.md` (ID-ссылки), базовый документ §5 (количественная модель).
Цель: дать точные определения, утверждения (с набросками доказательств) и вычислимые
формулы, которые MVP обязан проверять тестами/benchmark'ом.

## 0. Соглашения

- Множества: `U` (люди), `P_ops` (platform-operations subjects), `D` (definitions), `I` (installations), `R` (runtime instances),
  `Gt` (grants), `W` (workspaces), `O` (content objects), `Ev` (evidence), `Ka`
  (knowledge assertions). Все ID — из канонических пространств имён хаба.
- `W_shared = {w ∈ W | kind(w)=shared}`; только `W_shared`, не произвольный Workspace,
  может быть коллективным subject гранта.
- Время дискретно-непрерывное `t ∈ ℝ≥0`; события логически упорядочены happened-before
  [H16].
- Решения детерминированы: одинаковый вход + версия политики ⇒ одинаковый выход
  [seed:H14].

## 1. Граф отношений

**Определение 1.1.** *Identity-граф* — типизированный мультиграф
`Γ = (V, E)`, `V = U ⊎ P_ops ⊎ D ⊎ I ⊎ R ⊎ Gt ⊎ W ⊎ O ⊎ …`; рёбра помечены отношениями из §2
онтологии (`owns`, `installed_as`, `instantiated_by`, `acts_for`, `member_of`,
`located_in`, `supported_by`, …).

**Определение 1.2 (ReBAC-достижимость).** Для политики в стиле Zanzibar [C5][L17] право
выражается предикатом `can(actor, rel, resource)` и вычисляется стратегической оценкой
графа. Ядро политик хаба — стратифицированный позитивный Datalog [L14][L15]:

```prolog
% пример правил MVP (все - позитивная стратификация)
can(Act, read(O))      :- located_in(O,W), member_of(Act,W,viewer).
can(Act, write(O))     :- located_in(O,W), member_of(Act,W,editor).
can(R, act(S))         :- delegation(G), subject(G,S), actor(G,R),
                          active(G,t), within_scope(G,action,read(_)). % схематично
member_of(R,W,role)    :- acts_for(R,U,G), member_of(U,W,role), grants_actor_access(G).
```

**Утверждение 1.3 (разрешимость и сложность).** При запрете отрицательных рёбер в ядре
(анти-паттерн №5 онтологии; ядро — позитивные permit-выводы, запреты — отдельным
forbid/exception-каналом без операторов отрицания в условиях, как в Cedar [C8][C15]) оценка
монотонна: добавление факта не отменяет выводов; data complexity полиномиальна (semi-naive
evaluation), что согласуется с бюджетом p95 < 20 ms на графе ≤ 225 принципалов × ~10³ рёбер
[seed:§5].

**Утверждение 1.4 (workspace-медиация ограничивает связи).** Пусть `n = |I ∪ R|` агентов,
`k` workspaces; политикой хаба задан жёсткий предел размера workspace `m_w ≤ M_w`
членов-принципалов (люди + приглашённые агенты вместе; стартовое значение M_w = 8 —
параметр политики, а не следствие численности группы). Потенциальных направленных пар
внутри workspaces: `E_ws = Σ_w m_w·(m_w − 1) ≤ k·M_w·(M_w−1)`; при n=205, k=30, M_w=8:
`E_ws ≤ 30·8·7 = 1 680 ≪ 205·204 = 41 820` [seed:H13]. Сравнение консервативно по
популяциям: E_ws считает пары всех принципалов workspace (включая людей), all-pairs —
только агентов; вывод сохраняется при любом разумном M_w (даже M_w=20 даёт
E_ws ≤ 11 400 ≪ 41 820). Доступ возможен только если политика выводит
`can(actor, rel, resource)` из членства/грантов (§1.2): у пары без общего workspace может
существовать графовый путь в Γ через общего владельца, но он не порождает can()-вывода —
доступ требует новой явной грант/пригласительной операции.

## 2. Семантика authorize()

**Определение 2.1.**

```text
authorize(a ∈ R, s ∈ U ⊎ W_shared ⊎ P_ops, g ∈ Gt, α ∈ Act, ξ ∈ Res, p ∈ Run, κ_ctx ∈ Ctx)
  → δ ∈ {allow, deny, approval_required(q)} , q = конкретное требование
```

Порядок короткозамыкающей оценки (фиксирован, версия политики `πv` в каждом решении):

1. `auth(a)`: токен instance валиден и sender-constrained (DPoP-профиль [B6], mTLS [B7]).
   Провал → `deny`.
2. `healthy(inst(a))`: definition/installation не в quarantine/revoked и совпадает с
   актором гранта (`inst(a) = ι_a`). Провал → `deny`.
3. `valid(g, t)`: активна, TTL не истёк, budget > 0, jti не отозван [B12][B13]. Провал → `deny`.
4. `covers(g, α, ξ)` и `subject_ok(g, s)`: grant покрывает действие/ресурс/субъекта.
   Провал → `deny`.
5. `rel(a→s)`: ReBAC-вывод §1 даёт отношение. Провал → `deny`.
6. `attr(ξ, κ_ctx)`: классификация данных/риска/цели (ABAC-слой [C3][C13]). Высокий риск →
   `approval_required`.
7. `quota(a, run(p))` ≥ порога (token bucket §5). Провал → `approval_required` или `deny`
   по классу действия.
8. Атомарно: запись AuditEvent + решение (transactional outbox [H4]). Short-lived execution
   credential, производный от `g`, выдаётся только в ветке `allow`; для `deny` и
   `approval_required` фиксируются только decision/audit [B4].

**Свойство 2.2 (граница TOCTOU и доставки).** Шаги 3–8 атомарны относительно состояния
решения и гранта. Локальный consumer обязан в одной транзакции зафиксировать
`effect_receipt(decision_id)` вместе с эффектом; внешний consumer использует fencing token
или проверяемый precondition. Outbox доставляет at-least-once. Если внешний исход неизвестен,
система создаёт reconciliation case и не делает blind retry. Это закрывает повтор локального
эффекта, но не объявляет общей exactly-once семантики для внешнего мира [H6][I7].

**Свойство 2.3 (отзыв ≤ 5 c для новых действий).** Новое действие требует шага 3;
`revoke(g)` — транзакционная правка состояния, видимая любому следующему шагу 3 без
кэшей (TTL кэша решений = 0 для revoke-класса). Уже начатый long-action завершается по
saga-компенсации [H5]. Формально: `∀t' ≥ t_revoke: ¬∃δ=allow с valid(g,t')`.

## 3. Алгебра делегирования

**Определение 3.1 (grant).** `g = (σ, ι_a, A, Ξ, C, τ_exp, β, jti, cnf)`: субъект σ,
идентичность актора ι_a (ссылка на AgentInstallation — стабильный принципал; конкретный
runtime instance привязывается в authorize через `inst(a) = ι_a`), множество действий A,
ресурсов Ξ, контекстных ограничений C (время/сеть/классификация), срок, бюджет,
ключ-привязка [B4][B5][B6][B17][B18]. Обозначения: ι_a отличаем от переменной действия α;
Ξ — от множества инстансов R.

**Отношение ослабления.** На полных грантах `g ⊑ g'` («g не шире g′») ⇔
`A_g ⊆ A_g′ ∧ Ξ_g ⊆ Ξ_g′ ∧ C_g ⊇ C_g′ ∧ τ_g ≤ τ_g′ ∧ β_g ≤ β_g′`; компоненты jti/cnf/ι_a
в сравнении не участвуют, поэтому `(Grants, ⊑)` — предпорядок; частичный порядок возникает
на фактор-классе scope-проекций `(σ, A, Ξ, C, τ, β)` (два различных гранта с одинаковым
scope взаимно эквивалентны по ⊑).

**Определение 3.2 (композиция с резервом).** Пусть `β_rem(g)` — доступный остаток
родительского ledger, а `β_c` — бюджет ребёнка. Производный грант разрешён только как
`derive(g, Δ, β_c) = (σ, ι_a', A∩Δ.A, Ξ∩Δ.Ξ, C∪Δ.C, min(τ), β_c)`
при `0 ≤ β_c ≤ β_rem(g)`. Создание child grant и reservation выполняются в одной
serializable-транзакции с блокировкой строки родителя: `β_rem(g) := β_rem(g) − β_c`.
Отмена неиспользованного child grant возвращает только подтверждённый остаток; spent budget
не возвращается.

**Теорема 3.3 (ослабление и сохранение бюджета).**
`derive(g, Δ, β_c) ⊑ g` при допустимых Δ и β_c: пересечения/min не расширяют scope,
а `β_c ≤ β_rem(g) ≤ β_g`. Дополнительно для каждого родителя сохраняется
`spent_local(g) + β_rem(g) + Σ outstanding_child_reservation = β_alloc(g)`; reservation
остаётся полной до закрытия ребёнка, после чего его spent roll-up'ится в родителя, а
подтверждённый unused remainder возвращается; serializable reserve
не позволяет двум конкурентным derive() превысить остаток. Индукция даёт это свойство для
всего дерева делегирования. Ограничение глубины κ_grant — отдельное правило операции
`POST /grants:derive` (стартовое κ_grant=3; linked roles RT [B27], delegation depth
D1LP [B26]), а не шаг authorize(). Следствие: агент не может расширить scope или
размножить выделенный бюджет — формализация POLA [B29].

**Замечание 3.4 (почему не «speaks-for» в чистом виде).** Логика Lampson–Abadi `A speaks
for B` [L7][L8] выражает делегирование, но допускает транзитивные усиления при
неаккуратных handoff; хаб использует её как обоснование модели, а исполняет —
конструктивно, через derive() с лимитом κ_grant.

## 4. Бюджеты и ёмкость

**4.1 Token bucket (per agent/run)** [J3]: bucket `(r, B)`; при событии стоимости c:
`b(t⁺) = min(B, b(t) + r·Δt) − c`; отказ — строго после пополнения:
если `min(B, b(t)+r·Δt) < c` (иначе опустошённый ранее бакет ложно откажет,
хотя за Δt накоплено r·Δt ≥ c). Per-agent квоты = пара (r, B);
глобальный лимит внешних вызовов = агрегат с приоритетами.

**4.2 Fan-out и стоимость.** Стоимость мультиагентного fan-out эмпирически до ~15× против
одиночного чата [E16]; поэтому max_fanout F_max и max_depth κ_run входят в C гранта
(§3), а не только в конфиг платформы [seed:§5.1].

**4.3 Little's law для PDP** [J1]: `L_auth = λ_auth · W_auth`. Верхний профиль seed:
λ = 34 events/s, целевой (не измеренный) W_auth ≤ 20 ms ⇒ L_auth ≈ 0.68 одновременных вычислений решения —
узкое место не в авторизации, а во внешних вызовах (~82 вызова/мин) [seed:§5.1].

**4.4 M/M/c для пула исполнителей** [J2]: при загрузке U = λ/(cμ) время ожидания растёт
круто при U → 1; правило проектирования: держать U ≤ 0.8 ⇒ нижняя граница пула при
μ = 100 решений/s на воркера и λ_burst = 100/s есть c_min = ⌈100/80⌉ = 2; выбрано c = 4
как явный запас под пики и перекладывание задач (фактически U_burst ≈ 0.25).
Проверяется benchmark-профилем seed §5.3, не считается доказанным. Benchmark обязан
снять arrival/service distributions и p95 queue/auth latency; Erlang-C применяется только
если эмпирические распределения согласуются с M/M/c, иначе используется replay/simulation.

**4.5 Хвостовая задержка под fan-out** [J12]: p99 агрегата из k независимых ветвей хуже
максимума отдельных; контроль: ограничение k (F_max), таймауты+джиттер [J5], опционально
hedged requests для идемпотентных чтений проекций.

**4.6 Хранение.** Events/year = users·runs/day·events/run·365 [seed:§5.2]:
36.5M строк ≈ 36.5 GB/yr raw при 1 KB; authoritative audit хранит payload-min + SHA-256
digest артефакта; append-only Merkle tree с подписанными tree heads (RFC 6962-стиль [I15])
даёт inclusion/consistency proof стоимостью O(log n). Линейная prev_hash-цепочка сама по
себе дала бы O(n) доказательство и потому не используется как единственная структура.
Retention tiers: hot (90 дн) / warm / cold object storage.

## 5. Гейт знания: вероятностная и аргументационная семантика

**5.1 Beta-модель доказательств** [J9][J13]. Evidence пары (support s_i, oppose o_i) с
экспоненциальным затуханием λ_e (полураспад T½): 
`a(t) = a₀ + Σ s_i e^(−λ_e (t−t_i))`, `b(t)` аналогично. Постериор `θ ~ Beta(a,b)`;
промоушен разрешён iff `P[θ > θ_min] ≥ 1 − ε_gate` (по умолчанию θ_min=0.9, ε_gate=0.05),
и число независимых evidence units `n_independent ≥ 2` (heterogeneity [seed:§8 evaluator collusion]).
Evidence units дедуплицируются по `canonical_source_id`; зеркала/републикации одного
`publisher_id` попадают в одну `independence_group`, и каждая группа даёт не более
одного голоса для порога. Эти поля назначает отдельный доверенный Provenance Resolver по
versioned registry rules, затем они immutable; ingesting agent и evaluator не имеют права
их записывать. Promotion в одной транзакции считает distinct frozen groups и проверяет
separation evaluator↔resolver. Независимость — provenance-ограничение, не самоутверждение агента.
Стартовые параметры профиля §8: a₀=b₀=1 (равномерный prior), затухание λ_e=ln2/T½,
T½=30 дн. Пример достижимой комбинации: 32 независимых support от первичных источников
за первые сутки без oppose ⇒ a≈33, b≈1 ⇒ P[θ>0.9]≈0.97 ≥ 0.95, n_independent=32≥2.
Sanity-check: n_independent≥2 необходимо, но само по себе недостаточно — уже при нулевом oppose
требуется a≥29 (поскольку P[θ≤0.9]=0.9^a при b=1: 0.9²⁸>0.05≥0.9²⁹).

**5.2 Аргументационный слой.** Множество assertions Ka с attack-отношением образует AF
[F18]; статус promoted = принадлежность grounded extension (минимальный неподвижный
пункт монотонного характеристического оператора `F(S) = {x | ∀y: (y attacks x) ⇒ ∃z∈S:
z attacks y}`). Монотонность F гарантирует существование и единственность grounded
extension и его вычислимость итерацией за полиномиальное время; сам статус при добавлении
нового аргумента может измениться (пример: добавлена атака без защитника) — поэтому любое
добавление/оспаривание проходит через явную переоценку challenge-механизмом онтологии,
а не применяется «в фоне».
Приоритеты (ASPIC+ [F19]) задаются типом evidence (первичный источник > вторичный >
LLM-оценка); burden of proof по классам claim [F20].

**5.3 Правило доставки.** Message от пир-агента может создать только `PROPOSED`-запись
(ontology §3.2); формально оператор обновления знания установки — DEL action model [F12],
но публичное изменение возможно только через PromotionActivity. Revision vs Update
различаются: исправление claim = AGM-revision новой версии с superseded-связью [F14][F15];
изменение состава workspace = update без изменения claims.

## 6. Репутация и риск-контур approvals

**6.1 Репутация member→agent**: та же Beta-машина (§5.1) над исходами runs
(успех/нарушение квот/инциденты), затухание λ_r. Использование: рекомендации UI и
адаптивные пороги approval; НЕ входит в authorize() как источник власти (детерминизм
[H14]).

**6.2 Риск-скоринг для approval_required**: `R_risk = w1·class(res) + w2·width(g) +
w3·anomaly(z-score частоты) + w4·novelty(version diff)`; approval требуется при
`R_risk > θ(role, workspace_type)`. Анти-усталость: глобальный attention budget — не более
N_prompts/час на пользователя, пакетирование низкорисковых [K9][K7].

**6.3 Групповое агрегирование (опция)**: EigenTrust-подобная нормализация [J10]
допустима для рекомендаций, но устойчивость к collusion ограничена pretrusted-set
требованием; в MVP — off.

## 7. Свойства для верификации (Alloy/TLA+/simulation)

Alloy-инварианты (bounded check при design-time) [L10]; ссылки `инв.I#` — на инварианты
онтологии (`50_ontology.md`), чтобы не путать с источниками домена I:
- INV1 (identity separation, инв.I1): no v ∈ V участвует двумя классами одновременно.
- INV2 (single scope, инв.I3): каждый ContentObject имеет ровно одну located_in.
- INV3 (attenuation, инв.I2): ∀ производный g: g ⊑ родитель (проверка derive()).
- INV4 (no orphan promotion): promoted Ka имеет ≥1 evidence и ровно одну PromotionActivity.
- INV5 (revocation monotonicity): revoked grant не появляется в allow-следах после t_revoke.
- INV6 (budget conservation, инв.I5): spent + remaining + outstanding child reservations
  не превышают allocation ни при одном interleaving derive/revoke/exhaust.

TLA+-спеки (liveness/safety) [L11][L19]:
- SAF: каждое committed решение имеет outbox-event; повтор доставки не создаёт второй
  локальный effect_receipt, а unknown external outcome переходит в reconciliation [H4][H6].
- SAF: состояние grant меняется только через {approve, revoke, expire, exhaust}.
- LIVE: одобренный owner'ом грант становится active в течение одного тика планировщика.
- LIVE: crash между transition и publish восстанавливается replay'ем (event sourcing [H3],
  durable execution паттерн [H8]).

Deterministic simulation (FoundationDB-стиль [H17]): сидируемый планировщик + инъекция
падений; acceptance: 0 нарушений INV1–6 и SAF на 10⁶ смоделированных операций.

## 9. Ограничения модели

1. Все числа — плановые оценки; benchmark seed §5.3 обязателен до заявлений о
   производительности (H1/H10 остаются условными).
2. Beta-модель доверия чувствительна к выбору λ_e и к накрутке; применяется только в UX-
   контуре, не в enforcement.
3. Аргументационный гейт задаёт каркас; веса приоритетов evidence требуют калибровки на
   корпусе инцидентов (будущая работа).
4. Верификация (§7) — обязательство дизайна; спеки пишутся в MVP-фазе, здесь фиксируется
