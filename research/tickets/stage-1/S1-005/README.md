# S1-005 — QA1 runtime topology: modular monolith versus containers

Research ticket bundle for
[docs/RESEARCH_STAGE_1_TICKETS.md, section S1-005](../../../docs/RESEARCH_STAGE_1_TICKETS.md)
(research question, scope, non-scope, acceptance criteria). This work is
offline and stdlib-only: no LLM and no network were used to produce or verify
it.

## Research question

For the MVP, does a modular monolith with hard internal contracts provide a
better safety, determinism, and operability boundary than splitting the
runtime into containers?

## Decision recorded (QA1)

**Modular monolith** — one process, one SQLite/WAL store, the gateway as the
sole effects path, the journal as the single atomic transition+audit writer.
QA1 decision matrix: `modular_monolith` 36/40 vs `container_split` 21/40
across 8 explicit dimensions (policy gateway enforcement, audit atomicity and
chain, worker failure isolation, deterministic simulation/replay, SQLite/WAL
constraints, deployment/recovery, operational complexity, independent
scaling). Acceptance is lexicographic: the hard invariants (D1
policy single-authority, D2 audit atomicity) gate before totals are compared,
and a candidate that duplicates policy state or weakens the audit boundary is
rejected regardless of any superficial latency score. Migration triggers and
non-goals are recorded in the matrix recommendation and the platform plan.

## Probe design (adversarial, fail-closed)

- **`gateway-audit-invariants`** — parses the recommendation from the bundle
  matrix and verifies it preserves gateway-only effects, a single
  policy-state owner and atomic transition+audit; rejects a near-miss
  container split that duplicates policy state and buffers audit
  asynchronously **even though it reports 1.9 ms p99 versus the measured
  7.39 ms baseline** (latency is not an acceptance input); marks a
  modular-monolith recommendation that omits a failure boundary or the
  deterministic-simulation interface as incomplete; re-verifies all 9
  repo-local source SHA-256 bindings from disk.
- **`matrix-coverage`** — enforces the quantitative acceptance criteria:
  ≥6 dimensions (both options scored 1..5 with evidence), totals consistent
  with per-dimension sums, ≥3 complete failure/recovery scenarios, a single
  recommendation with explicit assumptions/migration trigger/non-goals,
  ticket claim-class coverage (`architecture_fact`, `tradeoff`,
  `design_inference`, `risk`, `decision`) mapped onto the harness classes
  (`fact`/`inference`/`assumption`/`target`), and no positive
  production-build / measured-reliability claim.

Both probes: **7/7 checks pass, exit 0, final JSON verdict
`{"status": "pass", "observed": "pass", ...}`** (2026-08-31).
